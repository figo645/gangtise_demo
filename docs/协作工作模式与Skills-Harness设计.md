# 洞见智研协作工作模式与 Skills / Harness 设计

版本：V1.0  
更新时间：2026-10-17  
适用范围：洞见智研代码、测试、产品文档、BDD 报告和生产问题协作

## 1. 重新设计的目标

我们之前的工作方式能够快速推进功能，但随着需求数量增加，出现了几个典型问题：

- 一个会话持续叠加多个主题，历史口径变长且难以区分当前结论；
- 需求、Bug、测试报告、架构讨论和产品文案交错，导致实现边界不清；
- 先生成报告、后补真实验证，容易出现“报告看起来完成但系统仍失败”；
- 同一能力多次重复实现，旧任务、旧入口、旧文案没有及时封存；
- H5、Web、大V后台和 Admin 的逻辑容易出现局部修复、跨端不一致；
- 技能和工具是“想到才用”，没有形成稳定的路由和证据标准；
- 长期上下文消耗大，但其中很多内容只是历史背景，不应每次重新加载。

新的工作模式不是让流程变重，而是让每次工作都快速回答四个问题：

1. 现在到底要改变什么？
2. 哪些现有能力应该复用？
3. 如何证明修改真的生效？
4. 哪些内容不在本次范围内？

## 2. 推荐的任务分层

每个新请求先归入一种任务类型。一个任务只允许一个主类型，其他内容另开任务或记录为后续项。

| 类型 | 典型请求 | 主要产出 | 首选 Harness |
|---|---|---|---|
| Feature | 增加功能、调整交互、改业务逻辑 | 代码、测试、变更摘要 | Shell + 定向测试，必要时浏览器 |
| Bugfix | 已知错误、日志异常、实际与提示不一致 | 修复、回归测试、根因 | Shell + 复现脚本 + UI 验证 |
| Verification | “确认是否完成”“真实 BDD”“生产一致性” | 测试结果、证据、报告 | 现有测试 + 浏览器/API 实测 |
| Review | 架构、性能、安全、设计评估 | Findings 优先的审查报告 | 静态扫描 + 查询 + 压测/页面证据 |
| Artifact | MD、HTML、CSV、PPT 脚本、手册 | 独立文件 | 对应 artifact skill + 结构校验 |
| Question | 解释概念、比较方案、估算 | 结论和假设 | 只读检查，默认不改代码 |

### 2.1 会话拆分规则

- 同一个 Feature 的连续修复可以留在同一会话。
- 出现以下情况时新开会话：换模块、换角色、换数据源、从实现转为架构评审、从代码转为大文档、上下文已无法准确区分当前需求。
- 需要保留连续性的任务，在新会话开头只提供“任务摘要、已改文件、未解决问题、验证命令”，不要复制全部历史对话。
- 父任务只保留目标和决策；细节 Bug 用子任务完成，完成后回写结果。

## 3. 标准任务包

每次编码任务都用以下最小模板启动：

```text
任务类型：Feature / Bugfix / Verification / Review / Artifact
目标：一句话说明最终要改变的用户行为
用户与租户：investor / dav / admin；tenant=...
涉及端：H5 / Web / 大V工作台 / Admin / API / Worker
当前现象：可复现步骤、接口或日志证据
期望结果：成功、失败、空状态和权限边界
复用要求：优先查找的已有能力、任务、API、表和测试
数据库边界：是否允许改表结构、主数据、业务数据
验收证据：测试命令、接口返回、页面截图或报告
非目标：本次明确不改什么
```

缺少信息时不应立即猜测实现。可以先做只读 Discovery；只有会影响数据模型、权限、外部 API 或用户体验决策时，才向用户提交 1 个简短方案选择。

## 4. 四阶段执行协议

### 阶段 A：Discovery

目标是建立事实，不写代码。固定检查：

1. 路由和页面入口；
2. Domain Service 和外部 provider；
3. 数据表、迁移和任务配置；
4. 现有测试、BDD 报告和复现脚本；
5. `git status` 与相关 diff；
6. 当前运行进程和本地服务状态（只有需要时）。

Discovery 输出三项：

- 当前真实链路；
- 最小修改点；
- 风险和未决事项。

### 阶段 B：Decision

在修改前明确以下决策：

- 是复用旧能力、重构旧能力，还是新增能力？
- 数据是共享快照、租户配置还是用户按需数据？
- 成功标准是 HTTP 成功、业务成功，还是用户可读结果？
- 失败时是重试、降级、停止还是展示空状态？
- H5、Web、工作台和 Admin 是否必须共享同一 API/Service？
- 是否涉及数据库结构、主数据、凭证或生产数据？

### 阶段 C：Implementation

实施原则：

- 先改领域服务和 API 契约，再改页面表现；
- 保持 H5/Web 使用同一业务服务，不复制逻辑；
- 外部调用集中在 provider 或 task，不放进页面组合函数；
- 状态至少覆盖 loading、success、empty、error、stopped/cancelled；
- 任何“成功但内容为空”的情况必须成为显式业务状态；
- 尽量一个功能一个垂直切片完成，而不是横向修改很多不相关文件。

### 阶段 D：Verification / Delivery

验证按风险而不是按习惯选择：

| 风险 | 最小验证 |
|---|---|
| 纯文案/MD | Markdown 结构、链接和 diff 检查 |
| 后端规则 | 单元/领域测试 + API 测试 |
| 权限/租户 | 正向 + 跨租户负向测试 |
| 定时任务 | 手动执行、重复执行、停止/取消、运行记录 |
| 外部 API |真实调用或录制响应、业务码、空内容、日期和 source 校验 |
| UI | 浏览器打开真实页面、加载/空/错误/成功状态和移动尺寸 |
| 性能 | 资源体积、查询耗时、连接池、API P95 或明确说明未压测 |

交付必须写清：改了什么、跑了什么、通过多少、未验证什么、是否改表、是否改主数据、还有什么风险。

## 5. Skills 路由设计

Skills 不应被当作“额外知识库”，而应被当作可复用的工作流入口。

### 5.1 选择规则

```text
先判断产出类型
  ├─ 代码/接口：终端 + 项目测试
  ├─ UI/视觉：ui-ux-pro-max + 真实浏览器验证
  ├─ CSV/需求/token：user-story-audit-csv / codex-usage-attribution
  ├─ PDF/DOCX/表格：对应 artifact skill + 渲染/重算
  ├─ Codex/Skills/Harness自身：openai-docs
  └─ 外部授权或用户屏幕：MCP / Codex App / CUA
```

### 5.2 本项目建议固定的 Skill 组合

| 场景 | Skill | 使用方式 |
|---|---|---|
| 用户故事和需求审计 | `user-story-audit-csv` | 保持既有 CSV schema，不随意增列 |
| Codex token/工时归因 | `codex-usage-attribution` | 明确统计范围、估算/实测口径和证据 |
| UI 设计与体验 | `ui-ux-pro-max` | 先设计状态，再实现 CSS/模板，再做真实页面检查 |
| Codex 自身配置/skills | `openai-docs` | 先官方文档，再本地规范；不凭记忆扩展产品行为 |
| PDF | `pdf` | 提取、渲染、视觉校验后再引用 |
| 表格 | `spreadsheets` | 保持公式、格式、重算和结果校验 |
| 产品演示视频 | `product-demo-video-editor` | 只使用已验证的真实能力和实际页面 |

### 5.3 Skill 何时不该用

- 不为了“看起来专业”给每个简单问题套复杂 Skill；
- 不用浏览器验证可以由本地测试准确覆盖的纯后端逻辑；
- 不用静态报告代替真实接口或页面测试；
- 不用通用文档生成流程修改代码；
- 不把某个 Skill 的输出当作系统事实，仍需以代码、测试和运行结果为准。

## 6. Harness 设计

Harness 的职责是为不同风险提供正确的执行环境，而不是让所有任务都用同一种工具。

### 6.1 Shell Harness：默认主路径

适合：搜索、读取、编辑、单元测试、API 测试、Git 检查、静态分析。

原则：

- 先并行读取相互独立的文件；
- 使用 `rg` 定位，不做无目标全库读取；
- 使用 `apply_patch` 编辑；
- 先定向测试，再扩展回归；
- 记录命令和结果，不只报告“已测试”。

### 6.2 Browser / Playwright Harness：用户体验证据

适合：真实页面、登录、H5/Web 响应式、点击反馈、图表、滚动、弹窗和富文本。

固定检查矩阵：

| 角色 | 设备 | 页面 | 必测状态 |
|---|---|---|---|
| investor | 手机宽度 | H5 | 首屏、空自选、盲盒位置、洞见、消息 |
| investor | 桌面宽度 | Web | 基本面、自选股、K线、预测和刷新 |
| dav | 桌面宽度 | 工作台 | 指标配置、播报、粉丝、互动统计 |
| admin | 桌面宽度 | Admin | 任务、模型、权限和运行记录 |

浏览器测试必须检查页面可见结果，不只检查 HTTP 200。

### 6.3 CUA / Codex App Harness：仅用于真实应用状态

适合：用户明确指向当前屏幕、需要操作桌面应用、需要打开 Codex 线程或查看 App 终端。普通本地代码和浏览器测试不应优先走 CUA。

### 6.4 外部数据 Harness

对于 Gangtise、LLM、新闻或其他外部 API，使用脱敏凭证、最小请求和可审计 trace_id。把验证拆成：

1. 鉴权可用；
2. 请求契约正确；
3. HTTP 和业务码成功；
4. 返回内容可读；
5. 日期/时段正确；
6. 本地写库和页面展示正确。

## 7. 如何减少上下文和 Token 浪费

### 7.1 当前模式的主要浪费

- 每个新问题都携带整个项目历史；
- 多次重复说明同一个产品决策；
- 代码修改、报告生成和产品讨论没有分阶段；
- 一次加载超大模板，实际只改几个区块；
- 反复生成静态报告，却没有先修复底层失败。

### 7.2 新规则

- 每个会话开头使用不超过 20 行的任务摘要；
- 只读取与当前验收直接相关的文件；
- 用 `rg`、函数名和行号定位，不重复读取整文件；
- 先修复根因，再生成最终报告；
- 旧决策写入项目文档，后续引用摘要而不是复制全文；
- 代码、测试报告和产品手册分开会话，除非同一交付物明确绑定；
- 结束时生成“已完成/未完成/证据/下一步”四段摘要，作为下一个任务入口。

## 8. 推荐的分支与交付策略

### 8.1 分支

- `codex/feature-<short-name>`：新功能；
- `codex/fix-<short-name>`：Bug 修复；
- `codex/docs-<short-name>`：文档和报告；
- 不为了每个小文案创建复杂分支，但涉及代码和数据库时必须隔离。

### 8.2 提交粒度

建议按垂直能力提交，而不是按文件提交：

1. 服务/API/数据契约；
2. 页面状态和交互；
3. 测试和报告；
4. 文档与发布说明。

这样可以单独回滚 UI、任务或数据源适配，而不需要回滚整个功能。

### 8.3 提交前门禁

```bash
git diff --check
python3 -m py_compile <changed-python-files>
pytest <target-tests> -q
pytest <related-regression-tests> -q
```

如果有真实页面改动，再补充浏览器检查；如果有数据库迁移，再补充 schema-only、升级顺序和回滚审计。

## 9. 适合洞见智研的标准工作流

```text
用户提出目标
  ↓
归类任务 + 确认角色/租户/端
  ↓
Discovery：找到现有能力和证据
  ↓
Decision：复用/重构/新增，明确非目标
  ↓
实现一个垂直切片
  ↓
定向测试
  ↓
真实页面或外部 API 验证
  ↓
受影响回归
  ↓
文档/报告/提交收口
```

### 9.1 以播报 Bug 为例

不能从“任务失败”直接改前端文案。正确路径是：

1. 检查 Gangtise 请求参数和返回 JSON；
2. 判断 HTTP、业务码、记录、时段标识和正文；
3. 确定空正文是否被错误当成失败；
4. 修正 provider/parser/domain 的成功语义；
5. 增加早报、午报、晚报和 fallback 测试；
6. 再检查任务记录、洞见、站内消息和大V/粉丝展示。

### 9.2 以 UI Bug 为例

不能只改模板字符串。正确路径是：

1. 确定页面实际入口和角色；
2. 查找渲染函数、CSS 定位和 z-index；
3. 检查移动宽度和滚动容器；
4. 修改组件位置和状态；
5. 浏览器验证初始位置、拖拽、遮挡和刷新；
6. 加入回归断言，防止 H5/Web 分叉。

## 10. 质量门禁与完成定义

一个任务只有同时满足以下条件才算完成：

- 目标行为已经实现，不只是文案或静态入口存在；
- 成功、失败、空状态和权限边界明确；
- 现有能力被复用或新增原因已记录；
- 相关端一致，或差异已明确说明；
- 定向测试通过，关键风险有回归测试；
- 真实外部接口或页面已验证，若无法验证必须明确写出；
- 未误改数据库结构、主数据、生产数据或凭证；
- 变更、验证命令和残余风险已交付。

## 11. 最终建议

我们后续应从“持续对话式开发”升级为“证据驱动的垂直切片开发”。具体就是：

1. 先把长会话拆成清晰任务包；
2. 先定位现有能力，再决定是否新增；
3. 用 Skill 处理可复用流程，用 Harness 提供正确执行环境；
4. 让测试和真实页面证据晚于实现、但早于报告；
5. 用项目级 `AGENTS.md` 固化不变量；
6. 用短摘要把结果传递到下一会话，而不是复制历史上下文。

这套模式不会牺牲迭代速度，反而会减少重复修复、跨端回归、假成功报告和上下文浪费。对洞见智研这种同时包含金融数据、租户权限、异步任务、AI 工具和多端 UI 的系统，**准确的边界和可复现的证据，比单次生成更多代码更重要**。
