一、监管式结论摘要

P0：身份凭证保护不达标。代码显示用户密码直接写入 users.password 并用明文比较；仓库还跟踪了 `.gangtise_session_secret` 和 `.gangtise_openapi_credentials` 等敏感文件。任何一个泄露都可能导致用户账号、会话或外部数据服务被接管。该问题应在对外生产和扩大用户前完成整改。
P0：Admin 用户接口存在敏感凭证回传风险。 /api/admin/users、用户创建、批量导入等接口直接返回 list_users()，而该函数查询并返回 password 字段。即使接口要求 Admin 权限，也不应把密码字段返回浏览器或前端状态。
总体判断：系统已有多租户、权限、任务、数据快照、审计日志和自动化测试基础，但当前更像“功能完整的投研应用 MVP”，还不是可以直接按金融机构生产控制要求运行的系统。最大缺口集中在凭证治理、身份安全、API 防滥用、数据治理、模型风险管理和可追责性。

从监管审慎角度，建议当前系统先定位为研究辅助和内容服务平台，严格避免对外表述为证券投资顾问、自动交易、收益保证或持牌金融服务，除非另行完成主体资质、业务边界和合规审查。

四、身份、权限与客户数据风险

1. 密码管理是最高优先级问题。当前 verify_h5_password_login 和 verify_platform_password_login 使用 compare_digest(数据库密码, 输入密码)；create_user 直接把输入密码写入 users 表。应迁移到 Argon2id、bcrypt 或 PBKDF2 等专用密码哈希，并设计存量用户强制升级、密码重置和泄露后的全量轮换流程。
2. Admin 用户列表不应返回密码。接口复用全字段用户对象，包含密码、微信身份和联系方式等敏感信息。应建立 public_user_view、admin_user_view 和 auth_user_view 三类 DTO，默认禁止序列化 password、密码重置材料、微信 openid/unionid 和不必要的手机号。
3. 租户隔离已有基础，但需从“代码约定”升级为“强制策略”。现有测试覆盖粉丝/大V关系和跨租户部分路径，属于积极信号；但 API 仍在多个文件中自行读取 tenant_slug。建议统一 AuthContext/Policy，并补充所有读写 API 的跨租户负向矩阵。

Admin 强认证当前以账号密码和会话为主生产 Admin 建议 MFA、IP/设备策略、敏感操作二次确认

五、数据源与市场信息风险

产品包含市场一览、热门行业、宏观指标、个股 K 线/分时、新闻和 Gangtise 投研能力。监管关注点不是“有没有数据”，而是数据是否有授权、可追溯、及时、准确，并且不会把历史或预测当作实时事实。

已具备的正向基础

  • 市场与行业存在后台任务和快照思路。
  • 个股分时、日K与预测已区分产品展示。
  • 页面有数据来源、同步时间和不可用状态的设计。
  • 现有测试覆盖 Gangtise 凭证、市场数据和指标同步场景。

仍需监管化治理

  • 建立供应商授权台账、接口用途和计费审计。
  • 统一 source/as_of/synced_at/freshness/status/trace_id。
  • 禁止页面缺缓存时隐式调用远程 API。
  • 记录旧值、修正值、数据异常和人工覆盖原因。
特别风险：HTTP 200、业务码成功、记录存在、正文可读、日期正确、写库成功和页面展示成功是不同层次。播报曾出现“接口成功但内容为空”的历史问题，说明系统必须将“可读业务结果”作为最终成功条件，并保留原始响应摘要和 trace_id。

七、内容、消息、付费与用户权益风险

内容发布：洞见、午报、晚报和站内信属于可能影响用户判断的研究内容，应保存原始材料、模型版本、人工修改、发布时间、数据时间、发布者和撤回记录。
订阅/付费：系统已有产品、订单、订阅和人工确认路径，但从监管角度还需要订单状态机、支付回调验签、权益开通审计、退款/撤销、到期和投诉处理。人工标记付费用户不能作为最终生产支付凭证。
营销口径：页面和大V内容必须避免“稳赚”“准确预测”“跟买”“保证收益”等表述；“红绿利好/利空”也应明确是规则或模型标注，而不是投资建议。
消息触达：播报推送应有租户开关、用户订阅状态、退订/免打扰策略、发送记录和失败重试，不能因为 Admin 和大V两个入口而重复推送。

九、日志、审计与可追责性

已有基础

  • 应用、Agent、错误日志已经分开建设。
  • 访问日志记录 IP、路径、方法、状态、UA、Referer 和租户/角色上下文。
  • 任务运行记录包含执行状态和错误摘要。
  • 洞见有发布、修订和置顶相关能力。

监管要求的缺口

  • 日志中的个人信息需要分级、脱敏、保留期限和访问审批。
  • 敏感操作需要操作者、前后值、原因、trace_id 和结果。
  • 日志应防篡改、集中存储并有告警，不只保存在本地文件。
  • 模型调用需要记录版本、输入摘要、工具、数据时间和输出状态。
审计重点：“谁在什么时间，以什么身份，在什么租户，对什么对象，做了什么操作，结果是什么”应成为所有发布、用户、权限、任务、支付和数据源操作的统一审计结构，而不是只靠普通应用日志。

十一、整改优先级与验收标准

阶段整改动作验收标准
立即从版本库和部署包移除敏感凭证；撤销并轮换已暴露的 Session/OpenAPI/Gangtise/数据库凭证；清理历史日志和备份中的副本。密钥扫描无命中；旧凭证不可用；生产应用从受控 Secret 管理读取。

上线前建立模型与数据源风险台账、可读结果契约、预测标识和模型输出审计。每个结果可回答来源、时间、版本、工具、输入摘要和失败原因。
30-60日建立统一审计事件、outbox、集中日志、数据留存、告警、备份恢复和压测基线。关键操作可追溯；RPO/RTO 有演练；API P95、任务失败率和数据新鲜度有告警。

十二、暂不建议对外宣称的事项

  • 不应宣称为“持牌证券投资顾问”或“自动化投资顾问”，除非主体和业务已获得相应资质。
  • 不应宣称预测准确、稳定盈利、收益保证、自动跟买或替代专业投资决策。
  • 不应把 Gangtise、AKShare 或其他供应商称为“绝对可靠”或“实时无误”，应以授权和数据 SLA 为准。
  • 不应在演示、日志、报告、前端或工单中展示真实 API Key、数据库密码、Session Secret 或用户密码。
  • 不应把功能测试通过、接口 HTTP 200 或静态报告通过写成合规认证或生产安全认证。

十三、最终监管式判断

当前系统的业务创新和工程基础是可见的，但安全控制尚未达到金融业务对身份凭证、客户数据、模型输出和操作审计的最低审慎要求。在完成 P0 项之前，不建议扩大真实用户规模、不建议开放高权限 Admin 给多人、不建议将系统包装为证券投资顾问服务，也不建议把现有模型预测和数据结果直接用于交易决策。

完成 P0 后，再按 P1 顺序推进 API 防护、文件/URL 安全、模型治理和审计体系。只有在权限负向测试、密钥轮换、灾备恢复、容量压测和模型风险评估均有证据后，才适合进入更大规模生产运营。

积极结论：现有 97 个针对性测试全部通过，说明团队已经具备租户、角色、内容和互动回归基础。下一步应把同样的严谨程度扩展到安全控制、敏感信息保护和监管审计，而不是继续优先增加功能。
