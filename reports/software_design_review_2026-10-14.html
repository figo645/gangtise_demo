二、总体架构判断

当前架构

浏览器 → Flask 页面/API → PostgreSQL；Gunicorn Web、独立 Worker、独立 Scheduler；市场、LLM、内容、消息等能力集中在 Python Domain Service 层。

这是适合当前规模的模块化单体（Modular Monolith），不是无结构的大单体。它比立即拆成 Node.js + Python 两个业务服务更稳妥。

设计原则符合度

单一职责6/10
依赖倒置/边界清晰6/10
数据一致性7/10
可观测性6/10
可测试性8/10
演进可扩展性6/10
正确方向：Web、Worker、Scheduler 已分离；任务状态落库；数据库连接在 app context teardown 关闭；共享市场快照、按需个股数据和租户配置已有明确建模。
主要结构风险：业务边界仍靠模块内函数约定维持，跨域导入和兼容回退较多；当用户、任务、数据源和功能继续增长时，变更容易产生隐性耦合。

三、按功能逐项评估

功能当前设计符合原则主要风险建议
登录、注册与角色Flask Session + PostgreSQL 用户；admin、dav、investor 角色；注册渠道、所属大V和账号管理已有能力。7/10角色判定和租户范围在多处 API 中重复处理，容易出现 H5/Web/Admin 口径漂移。集中为身份上下文与 Policy 层；所有租户资源强制使用统一 scope helper。
租户与粉丝关系用户含 tenant_slug，消息、评论、自选股和统计已有租户过滤。7/10历史兼容数据和前端 bootstrap 同时存在；关系约束依赖迁移与代码双重保证。补充跨租户负向测试、数据库 FK/唯一约束审计和统一 repository。
自选股与个股详情用户级持久化自选股；K线/分时按需获取；支持标注、评论、分析和预测。7.5/10缓存缺失时搜索链路仍可能触发远程 provider，页面读取与外部 API 边界不够纯。页面组合只读本地快照；远程搜索/刷新只能由明确 API 或任务触发，设置超时、熔断和限流。
市场、热门行业、宏观指标统一快照、任务同步、租户选择配置、页面读取数据库。7.5/10数据源历史上经历 AKShare/Gangtise 切换，兼容回退多，容易出现“同步成功但展示旧值”。统一 provider contract、source/version/as_of 字段和数据新鲜度 SLA；禁止隐式回退。
新闻聚合与标注新闻源聚合、过滤、去重、V4 标注和行业映射。6.5/10新闻源解析、规则、LLM 和统计集中在大模块；外部 200 不代表内容有效，异常分支复杂。拆成 source adapters、normalizer、classifier、publisher 四层，记录每步质量指标。
小金智能体/Hermes意图、工具计划、Gangtise 工具、LLM 严格绑定、会话和异步任务已有体系。7/10工具编排、提示词、模型配置和兼容逻辑仍大量集中在 AI service；SSE/JSON 多契约并存。建立统一 Agent Runtime contract；工具只返回结构化结果，编排层统一超时、重试、trace_id 和错误码。
洞见笔记与复盘草稿、URL/文件/语音输入、富文本、审核、发布、修订、置顶、消息通知。7.5/10发布是多个副作用组合；正文、消息、广播、粉丝线程的最终一致性需要更清晰。采用发布事务 + outbox/event delivery；版本、发布状态和通知状态分离。
消息与互动消息线程、广播、粉丝互动、评论分析和租户隔离。6.5/10消息中心既有领域表又保留历史 JSON 兼容路径，读写分支复杂。逐步完成 JSON compatibility sunset；以 message domain 表为唯一读源。
盲盒答题与统计题库、随机发放、重复作答、得分、题型统计和大V观察。7/10统计查询随着作答量增加可能变重，题目发放幂等性需持续验证。按 user/day/question 建唯一键；预聚合用户和题型统计，异步刷新图表。
Admin/大V任务中心统一任务配置、运行记录、手动执行、暂停/重启和 Scheduler 统一调度。7.5/10任务代码和业务实现仍有历史重复命名/兼容逻辑；停止状态与运行进程需严格区分。任务状态机标准化；每个任务定义 owner、锁、幂等键、超时、重试和取消语义。
商业化与二维码注册产品、订单、订阅、邀请码和注册入口已有数据库模型。6.5/10支付核验、权益开通和邀请注册属于高风险业务，目前更像 MVP 级闭环。增加订单状态机、支付回调验签、审计日志、权益快照和过期任务。

四、性能评估

领域现状判断影响优先级
首屏 HTML/JSH5 模板约 1 MB，单体脚本约 800 KB；Web 复用 H5 壳体。5MB 带宽环境下首屏解析、下载和执行都偏重。P1
首屏数据已做 bootstrap 精简和 Web 延迟 Dashboard，但仍有多个指标/新闻/配置初始化。数据库查询和 JSON 序列化可能叠加，慢登录仍有风险。P1
数据库连接池和 teardown 已有；大量领域查询、JSONB 兼容、统计查询并存。连接数、慢查询、重复聚合是主要不确定性。P1
外部 APIGangtise、AKShare、LLM 有缓存/任务/按需路径，但仍有 fallback 和直接调用边界。外部延迟会串入页面或任务；错误容易表现为“200但无内容”。P1
后台进程Gunicorn + Worker + Scheduler，启动脚本已具备 PID/停止/锁。内存总体可控，但 Python 大模块和多个 sidecar 会放大 RSS。P2
缓存有进程内缓存、数据库快照和 no-store API；未见统一 Redis 缓存层。多进程之间缓存不共享，部署扩容后命中率和一致性不稳定。P2
性能判断：当前最值得优化的是“首屏和数据查询”，不是先增加 Node.js。Node.js 只会增加一跳服务，不能解决 Python 端大模板、数据库聚合和外部 API 等主瓶颈。

五、可扩展性评估

可扩展性优点

  • 领域模块已经分出 market、AI、commerce、knowledge、quiz、workbench。
  • 任务配置和运行记录落库，可持续加入新任务。
  • PostgreSQL 迁移顺序和测试体系较完整。
  • 前台能力通过 API 与 bootstrap 状态组合，具备逐步前后端分离基础。

扩展瓶颈

  • 核心 Domain Service 文件过大，新增功能容易产生跨模块修改。
  • 模板中同时存在 HTML、CSS、JavaScript 和状态管理，前端复用困难。
  • 数据库访问没有统一 repository/query service 边界。
  • 进程内缓存无法支撑多 Web 实例共享失效。
  • 发布通知、外部同步等副作用还缺少统一事件总线。

建议目标：先把当前系统治理为“模块化单体 + 可独立扩展的 Worker”，等 API 契约稳定、性能指标达到瓶颈后，再按数据同步、Agent Runtime、通知投递等边界拆服务。

维度评价观察
角色体验较好H5、Web、大V和 Admin 有明确入口，部分能力保持一致。

内容可读性较好洞见颜色、标签、富文本和修订标识已有产品化处理，但模板与 CSS 分散容易回归。
可访问性不足有部分 aria-label 和键盘处理，但大型动态区域、错误提示、焦点管理和对比度尚未形成统一规范。

七、技术栈评估

技术适配性建议
Python 3.10 + Flask 3适合当前阶段业务开发效率高；继续强化蓝图、服务接口、类型检查和边界测试。
Gunicorn gthread可用适合当前 I/O 型请求；通过压测确定 worker/thread，不要用经验盲目加进程。
PostgreSQL + psycopg2合适核心数据、任务、消息和 JSONB 均适合；补充慢查询监控、连接池上限和索引审计。
Jinja + 原生 JavaScript短期可用，长期受限建议先拆分模块和资源，再考虑 React/Vue；不建议为换 Node.js 而整体重写。
ECharts / Quill适合应统一本地资源、版本和按需加载，避免 CDN 依赖影响生产可用性。
AKShare / Gangtise / LLM需适配器化以统一 provider contract 屏蔽供应商，明确实时性、失败、空内容、计费和回退规则。
Docker/启动 shell能运行，运维仍偏手工逐步迁移到 systemd/Supervisor/Kubernetes 任一规范进程管理，统一健康检查和优雅停止。

八、当前必须关注的问题

P1：页面读取路径仍可能触发远程市场搜索。
全量测试失败 test_page_watchlist_catalog_never_fetches_a_provider_when_cache_is_missing。页面组合函数在缓存缺失时进入 Gangtise 搜索，违反“页面只读快照、远程调用由显式刷新/任务负责”的边界，可能造成首屏慢和外部 API 消耗。
P1：首屏前端单体过大。
H5 模板和脚本承载多个产品面、状态、渲染器和 API 调用。应继续拆成 shell、feature chunks，并将 Dashboard、Hermes、Workbench、知识库按进入页面后加载。
P1：外部数据成功语义不够统一。
HTTP 200、业务成功、内容可读、数据日期和数据源有效性应分开建模，否则会重复出现“接口成功但播报失败/指标为空”的问题。
P2：兼容路径较多。
JSON 旧字段、数据库表、模拟数据清理、AKShare/Gangtise 回退和旧客户端兼容逻辑增加了认知负担。需要设定弃用周期和迁移完成指标。
P2：缺少生产级容量基线。
已有大量 BDD 和单元测试，但尚未替代真实压测。应建立 10/50/100 并发、首屏 TTFB、API P95、DB pool 使用率、RSS 和外部 API 延迟基线。
P2：异步副作用没有统一事件投递层。
发布、通知、广播、粉丝线程、嵌入和统计之间仍有多个 try/except 组合。应增加 outbox 或可靠任务事件，避免“主记录成功但前端误报失败”。
P2：鉴权/租户范围需要统一中间件。
目前各 API 自行检查角色和 tenant_slug，虽有测试覆盖，但重复逻辑容易产生边界遗漏。

九、建议路线图

阶段目标具体动作完成标准
现在至 2 周稳定边界与首屏禁止页面路径远程调用；统一 provider 结果契约；修复当前 1 个失败测试；压缩/拆分首屏资源。全量测试 0 fail；首屏 API 无外部调用；TTFB/P95 有基线。
2 至 6 周治理领域边界拆分 market provider、news pipeline、agent runtime、review publishing；引入统一 auth scope 和 task state machine。核心模块可独立测试；新增功能不直接修改超大核心文件。
6 至 12 周支撑用户增长引入 Redis 或等价共享缓存；增加 outbox/event delivery；建立压测、慢查询、队列和外部 API 监控。多 Web 实例可扩展；关键 API 有 P95、错误率和新鲜度告警。
之后选择性拆服务仅在指标证明需要时拆数据同步服务、Agent Runtime 或通知服务；前端再评估 SPA/Node BFF。拆分有明确容量收益，不以技术偏好驱动。

十、最终结论

当前软件设计符合模块化单体的合理实践，但还没有达到高并发、多人协作和快速独立交付的成熟平台级水平。继续使用 Python + Flask + Gunicorn + PostgreSQL 是合理的；优先治理首屏、数据源边界、异步发布一致性、统一鉴权和大模块拆分，比新增 Node.js 前端服务更能改善性能与可扩展性。

Node.js 可以作为未来独立前端构建/SSR/BFF 的选择，但不应作为当前性能问题的直接解法。当前最重要的工程动作是让页面只读快照、让任务负责采集、让 API 返回可验证的数据新鲜度、让异步副作用具备可靠状态。
